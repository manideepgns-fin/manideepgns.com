How I build

I don't write code. I direct it.

Since January 2026 I have built the software my finance team runs on by describing it in plain English and reviewing every change an AI makes. These are the rules that held up, one real change from start to finish, and the tools underneath. None of it depends on one model.

Eight rules

Plain rules for directing any AI model on real work. Each comes with the reason it exists.

  1. English is the only language I need.

    I describe what I want and why, in plain words. The AI explains its choices back the same way: short sentences, no jargon, the trade-off in terms a finance person would use. If I can't follow the explanation, the work isn't done.

    Why: I can't review code line by line. I can review a clear argument.

  2. Propose, don't ask.

    "Here's what I'd do, and why" beats "what would you like?" One strong recommendation is better than a menu of five. Questions come once, before the work starts, all together.

    Why: I bring the problem and the judgement. A menu of technical options hands the hard part back to the one person least able to choose.

  3. The task is the whole job.

    Something odd spotted on the way gets one line in the summary, not a detour. The test before any extra work: would the task ship wrong, or not at all, without it?

    Why: a useful side discovery can still eat the afternoon. It gets noted, and the task ships first.

  4. Check the source, not the memory.

    Before saying something is missing or broken, open the real thing: the live data, the actual document, the current docs. A model's memory of how a system works is a guess.

    Why: some errors disguise their cause. A failure on the server can show up in the browser as an unrelated access error, and a guess fixes the wrong thing.

  5. Fix the cause, then guard the whole class.

    Every bug gets traced to where it starts, and fixed there. Then it gets an automatic check that would catch every bug like it, not just this one.

    Why: one stray character in a prompt template silently broke a feature for three months. Now a test checks every template.

  6. Trust the check, not the claim.

    "Tests pass" is a claim until someone runs them. Every check an AI says it ran gets run again before anything ships, by one named reviewer.

    Why: agents have described test runs that never happened.

  7. Ask before anything that can't be undone.

    Building, committing and shipping run without asking. Sending email to customers, spending money, deleting data or changing live records always waits for a yes.

    Why: an automation once sent reminder emails that should never have gone out. That kind of send is now blocked unless I approve it.

  8. Write it down for the next model.

    Anything worth knowing about the business or its systems goes into the project's own files when it is learned, not into a model's memory. Any model that opens the project tomorrow inherits the same context.

    Why: a model forgets between sessions, and a different model never knew. Files don't forget.

One change, end to end

This website's redesign, in October 2026. A few hours, about a dozen decisions from me, no code typed by me.

  1. My portfolio is only dark. Can we have a light version?

    The first finding: colours were typed out by hand in dozens of places. Before any new theme, every colour moved into one named list, so a theme becomes one set of values.

  2. We need better colour usage.

    The first light version was a cream page with an orange-red accent. Correct, but forgettable. The second tried four colours, one per idea.

  3. Design it as if I hired a senior designer.

    A design checklist came back with the opposite of the second attempt: one colour, used with confidence. Day became navy ink and one ultramarine. Switching themes spreads the new sky out from the button you clicked.

  4. Is this actually senior grade?

    The honest answer was no: about seven out of ten, with six named gaps, the biggest being a case study with no real product in it.

  5. Try this open-source drawing skill.

    Its code was read before it was installed. It built the interactive machine on the Atlance case study, and its checks caught two real faults: a sheet drawn in front of a post that should hide it, and a script that printed its own code onto the page.

  6. Use real screenshots.

    Taken from the live product, and every row count blurred before anything was published.

  7. Ship it.

    Released, then checked on the live site. The first check failed because the host strips page comments the check was looking for. It was rerun on visible text, and passed.

The work was mine: the brief, the pushback, the taste and the yes. The typing wasn't.
